# MGS1 VR: Master Collection port, what we built and what the GOG (Integral) mod can take from it

Report date 2026-10-12. Covers the Master Collection (MC) port from 2026-10-07 to 2026-10-12, builds `mc_probe_v6` to `mc_hud_v2`.
Target: METAL GEAR SOLID, Master Collection (Steam), US 1.0 (SLUS-00594) first, PAL (SLES-01370) kept in step.
Test rig: Quest 2 through Virtual Desktop (VDXR 1.0.10, wireless then wired), RTX 3070, 90 Hz.

This report has three uses:

1. A record of how the MC port works and every problem we hit (with the evidence and the fix).
2. **A list of findings that apply directly to the GOG/Integral mod.** Several are bugs or weak spots the GOG mod very likely has too.
3. Reference data: addresses, structures, settings and the build and verification process.

Sections 3 and 4 hold the GOG-relevant material. Read those first if you only want what to improve.

## 2. How the MC port works

### 2.1 Where the game lives

The MC is M2's emulator running the original PS1 disc. All game logic is MIPS code in emulated PS1 RAM.

- The DLL is a `dinput8.dll` proxy (the game imports only `DirectInput8Create`). It finds PS1 RAM by scanning for the committed region of size `0x211000`. The RAM itself starts at base `+0x60`.
  - The emulator also keeps a lagging copy of RAM. Always use the copy that changes.
- Version detection:
  - US 1.0: "KETCHUP" at `0x800ADC98`.
  - The product code is at `0x80010000`.
- **Hooks are MIPS routines written into spare RAM.** A `jal` in the game is redirected to our routine.
  - The routine does its work, then tail-jumps to the original callee.
  - It is re-applied every 250 ms, because overlays reload.
- **Every routine is generated by a Python assembler script (never hand-assembled).** Each one is:
  - disassembled with capstone;
  - emulated with unicorn against real RAM snapshots from both versions;
  - byte-checked inside the built DLL.

  A hand-copied word was wrong once in phase 1; the generator-only rule exists because of it.

### 2.2 Threads (DLL)

- **Main thread:**
  - RAM discovery;
  - hook install and maintenance;
  - mode decision (off, head-look, Snake's eyes);
  - the cutscene cast lookup;
  - ini reload every 2 s, or at once after a panel change.
- **Writer thread** (1 ms loop): the *only* writer of game RAM.
  - It writes the head matrix (double-buffered slot plus sequence number), then the mode, the pad mailbox and the stereo half-offset.
  - It also applies body follows head.
- **XR thread:** OpenXR session (standard loader, D3D11).
  - head and hand poses, input actions;
  - picture intake, drawing, layer submission;
  - the settings panel and wrist panels.
- **Perf thread:** PDH counters (GPU 3D, video encode, CPU, network send) for the PERF log line.
- **Menu thread:** Quest buttons as DirectInput keys while the PS1 game is not running; F5 and F11 keys.
- **Present hook** (IDXGISwapChain Present / Present1, vtable 8 and 22): copies the game's backbuffer into a shared slot (2.4).

### 2.3 The camera routine (current: v11)

- **Hook:** the world camera's `jal TransposeMatrix`, in two places: DG_MakeCameraMatrix (gameplay) and FrameRunDemo (cutscenes).
- **It acts only when `a0` is the world eye** (`DG_Chanls[1].eye`). Then it:
  - **Mode 1 (head-look):** sets `eye = eye × M`.
  - **Mode 2 (Snake's eyes):** sets `eye = M` and positions the eye.
    - x and z come from Snake's head joint (DG_OBJS objs[6].world.t); y comes from GM_SnakeCamera.y, plus offsets.
    - It also writes `PadOrg = heading + 2048`, so the stick walks where you look.
  - **FOV override:** chanl `+0x50` (screen distance), default 120, which gives 106°.
  - **Stereo block:** described in 3.3.
- **Mailbox** at `0x8000A400`:
  - double-buffered M with sequence numbers;
  - an 8-entry ring of the seq applied per frame;
  - offsets, PadOrg, the Snake DG_OBJS pointer.
- **Code layout:**

  | Region | Contents |
  |---|---|
  | 0x8000A480 | main routine, 169 words |
  | 0x8000A780 | pad mailbox |
  | 0x8000A7A0 | pad routine, 96 words |
  | 0x8000A940 | stereo mailbox |
  | 0x8000A9D0-0x8000AC08 | stereo block |

- **Spare RAM** (watched live, never written by the game): `0x8000A400–0x8000B070` is free through s00a.
  - `0x8000FAA0–0x80010000` is used at boot. Not safe.

### 2.4 The picture path

- **Game side** (Present hook):
  1. Copy the backbuffer (1920×1080 BGRA) into one of **three** plain `MISC_SHARED` textures.
  2. End an EVENT query.
  3. Publish the slot *only after the query completes* (polled on the next Present).
- **XR side:**
  1. Claim the newest slot (Dekker-style claim, then re-check).
  2. Copy it to a private texture, plus the per-eye textures.
  3. Hold the slot until its own query completes.

  Neither GPU queue ever waits on the other (see 3.1).
- **Crop:** the auto crop is a centred 4:3 of the 224 visible of 240 lines. At 1080p that is 240,36,1440,1008.
  - Rows 0 and 1 are trimmed further because they hold the marker (3.2).
  - The projection FOV's top angle is reduced to match.
- **Submission:** one projection layer, 2880×1080 (two eyes of 1440×1080).
  - Each eye's view pose is the head pose its picture was drawn with, plus ±IPD/2 for stereo pictures.
  - FOV is exactly the game's:
    - `tan_h = 160/screen`;
    - `tan_v = (112·64/58)/screen` (DG_AdjustOverscan squeezes rows 58/64).
  - The compositor's reprojection does the world lock.
- **Optional quad layers:**
  - the settings panel, only while open;
  - two wrist panels, only when looked at.

### 2.5 Input

- **Pad:** a MIPS routine wraps the frame loop's `jal GV_UpdatePadSystem`. It calls the real one, then merges VR buttons, edges and the stick into `GV_PadData[0]` and `[2]`. The stick direction is `dir = angle + PadOrg`.
  - It is gated by GM_GameStatus `0x58000000` and DG_UnDrawFrameCount, so cutscene skipping still works.
- **MC launcher menus** (not PS1 code): the dinput8 proxy wraps `IDirectInput8::CreateDevice`, then the keyboard's GetDeviceState and GetDeviceData. Quest buttons are injected as keys only while the PS1 game is not running.
- **Hand poses:** OpenXR grip-pose action spaces for both hands. Used by the wrist panels now, and by motion controls later.

## 3. Findings that matter for the GOG/Integral mod

Each finding gives: what happened in MC, the evidence, and what to check or change in GOG.

### 3.1 Frame-rate collapse: the cause was a cross-device GPU wait, not quad layers

**MC history:**
- Several builds collapsed to 1/8 rate: xrEndFrame blocked 70–100 ms every frame while every CPU step was under 1 ms.
- We first blamed world-locked quad layers. The GOG notes say "one extra quad layer collapsed the frame rate".
- Switching to a projection layer helped gameplay, but menus stayed at 10–45 fps.
- Our PERF log (PDH counters) then showed the PC was never busy: GPU 3D 14–51%, encoder ≤76%, CPU ≤25%.

**Cause:** the picture hand-off used a keyed mutex. `AcquireSync` on the XR device inserts a **GPU-timeline wait** for the game's copy.
- That copy sits in the game's queue, which can be stuck behind its own vsync-blocked frames.
- The compositor then waits for our frame's GPU work, so xrEndFrame blocks.
- None of this shows as CPU time or GPU utilisation, so it looks like "VD/wireless lag".

**Fix:** three plain shared slots, completion tracked with EVENT queries on both sides, and publish only when the copy is finished.
- Result: xrEndFrame dropped from 60–100 ms stalls to about 1.2 ms.
- The headset held a steady 90 fps (wired), even with quad layers present (panel and wrist).

**For GOG:**
- Audit every cross-device or cross-thread hand-off for an implicit GPU wait: keyed mutex, shared handle plus Flush, or a CopyResource whose source is still being written by another device or queue.
- GOG's D3D9 capture feeds a D3D11 submit path, which is exactly this shape.
- If GOG ever showed "frame-rate collapse when a quad is added" or "menus slow", re-test with a non-waiting hand-off before blaming the compositor.
- The rule "quad layers are too expensive" may be wrong. In MC, quads cost nothing measurable once the wait was gone.
- Add a PDH perf line (GPU 3D / encode / CPU / network send). It turns "is it the PC or the stream?" into a log reading.

### 3.2 Instrument the output: tag each picture with its eye and head pose *inside the pixels*

This is the most important transferable finding.

**MC history:**
- Stereo v1 and v2 tagged each captured picture by reading the mailbox ring at Present time, with a "tag_delay" guess. The owner reported:
  - near objects shaking (stereo v1);
  - a slight doubling when moving the head, with stereo on *or off* (v2). This was also the "shimmer" reported earlier in mono.
- We then drew a **marker into the frame itself** and read it back from the captured picture. The marker is three 3×2-pixel TILE prims at screen (0,0), (3,0) and (6,0):
  - **eye colour:** red left, green right, blue mono;
  - **magenta:** a validator, so the reader can tell a marker from scene pixels;
  - **pose number:** the low 6 bits of the head-pose sequence number used for that frame, 2 bits per channel at levels 0/85/170/255. These survive PS1 15-bit colour, upscaling and blur.
- **The measurement:**
  - The old timing guess put the wrong eye on **50%** of pictures (MARKER line: "matched 90, missed 90").
  - It put the wrong head pose on **100%** of pictures, by **4.5 poses on average (about 50 ms at 90 Hz)** (POSE line).
- With the marker, doubling and shimmer were gone: "This feels perfect now!"

**Why the guess was wrong:** M2 presents every 30 fps game frame twice, and the emulator runs ahead of Present. The ring advances between the frame being drawn and the frame being shown, by a variable amount.

**For GOG:**
- GOG uses the same kind of timing-based tagging: FrameViewRecord, `stereo_pose_tagging`, an eye-tag timeout of 120 ms, and "capture skip count must be odd".
  - The handoff lists traps that look exactly like mis-tagging: "a stale tag sent a whole cutscene into one eye", "an even skip count blinded one eye", ghosting while moving.
  - **Measure it.** Draw a marker into the game's own frame and compare it with the current tag. It is cheap to try.
- **How to draw a marker in GOG:** inject a tiny rectangle into the frame the game renders. Options, roughly in order of robustness:
  - (a) Add a draw call in the D3D9 / DirectDraw wrapper at the end of the game's frame, *in the same render target, before the copy you capture*.
  - (b) Add a 2D prim to the game's own overlay list, as MC does with DG_Chanls[2].
- **Encoding:**
  - Use a validator colour block next to the data block.
  - Read the corner region back with a small staging copy taken with the frame, decoded when the GPU copy is known complete. No stall.
  - Search each tile only within its own strip: the data colour can look like the validator (we hit this; strip-limited search gave 0 errors over 576 test cases).
  - 2 bits per channel at 0/85/170/255 is robust. More bits per channel may also work on PC (24-bit colour), but test with blur first.
  - Hide the marker by cropping its rows, and adjust the projection's top FOV angle to match the crop.
- Once each picture carries its eye and pose:
  - the eye timeout becomes a pure safety net;
  - the motion hold can be relaxed, because rotation is fully corrected by exact pose tags (see 3.4).

### 3.3 Alternate-eye stereo: choose the eye by the draw buffer, not a toggle

**MC design:**
- The eye is chosen by `GV_Clock` (the frame's double-buffer index): buffer 1 = right eye (+IPD/2 along camera right), buffer 0 = left.
- The offset is applied in the camera routine to `eye.t` along the eye matrix's column 0, so the game re-rasterises with real parallax.
- Each picture is routed by its marker colour into a per-eye texture. Mono pictures go to both eyes.
- The view pose for a stereo picture is its tagged head pose plus ±IPD/2 along head-right, so the compositor reprojects each eye from where it was really drawn.

**Why not a toggle:**
- A toggle can drift from what is actually displayed (skipped frames, double calls per frame, pauses).
- The draw-buffer index is tied to the frame that will be shown.
- In GOG, the equivalent anchor is "which back buffer / which flip". Better still, use the marker colour (3.2).

**Movement hold (MC v1 bug, relevant to GOG's hold logic):**
- The first hold compared eye positions "two samples apart, assumed same eye". It sampled on head-pose arrival, not per game frame, so it mixed eyes.
- The 64-unit IPD jump read as movement, so stereo flipped on and off constantly: 78–90 times per 3 s while standing still.
- **Fix:** sample per game frame (GV_Time stamp), and only compare frames an even number of frames apart (same buffer, so the same offset).
- GOG's notes already mention un-applying last frame's offset before measuring. Verify that the hold isn't still firing from its own offset or from double samples. Log the trigger counts per 3 s, as MC's STEREO line does.

**Defaults that work:**

| Setting | Value |
|---|---|
| ipd_mm | 64 |
| units_per_m | 1000 (about 1 unit = 1 mm, unconfirmed) |
| hold_units | 20 per frame |
| hold_deg_s | 300 |
| hold_ms | 330 |
| eye_timeout_ms | 120 |
| min_fps | 20 |
| right-stick turning | always holds mono (the turn is not in the head pose) |

### 3.4 Pose tagging precision matters even in mono

The doubling appeared with stereo **off**. A world-locked picture posed at a head pose about 50 ms old jumps against the world when the head moves.

**For GOG:**
- If any residual judder or "shimmer" remains in mono first person, suspect the pose tag before the compositor or SSW.
- The same marker-based pose number fixes it.

### 3.5 Present cadence and emulator timing (MC-specific, with a GOG analogue)

- M2 presents 60/s while the US game runs at 30 fps (each frame twice). Earlier the headset loop also had "frames reused" counts.
- Instrument both: pictures taken per 3 s, frames reused, presents skipped, waits on our own copy. MC's PICTURE line does this.
- A quiet bug we found: the XR-side copy query was never flushed, so half of the headset frames waited on our own copy and picture intake halved. **Always Flush after ending a query you will poll with DONOTFLUSH.**

### 3.6 Cutscenes through Snake's eyes: data path and traps

**Data path** (decomp-verified, MC addresses in section 5):
- `FrameRunDemo(MGSDEMOACT* act, DMO_DAT* dat)`. At its `jal TransposeMatrix`, `s3 = act` and `s2 = dat` in both US and PAL.
- `act+0x30`: DMO_DEF*.
  - n_models at +0x10;
  - DMO_MDL[] at +0x18 (a GV_Malloc'd copy after init), stride 0x14, filename hash at +0xC.
- `act+0x34`: DEMO_MODEL[], stride 0x1A4. DG_OBJS at +0x7C (OBJECT follows the 0x7C CONTROL).
- Snake is identified by the filename hash: `GV_StrCode("snake") = 0x992D`.
  - The **tuxedo bonus also uses 0x992D**: the outfit swaps the file behind the same name.
  - `sne_nude = 0x34C2`.
- Visibility: `DG_OBJS.flag (+0x28) & 0x80` (DG_FLAG_INVISIBLE). If he is invisible or not cast, fall back to the director camera plus head-look.
- Head: joint 6 world matrix at DG_OBJS +0x270 (t at +0x284).
  - **Facing = atan2(m02, m22)**, i.e. column 2 of the head matrix. Checked against the player's rot.vy: within about 1°.
- Re-face on a new cutscene, when Snake is back on set, or on a head jump over 1500 units (a camera cut). Each re-face also recentres the head.

**Traps found:**
1. **The camera is computed twice per cutscene frame:** once by FrameRunDemo and once by the camera actor. A "last caller" record is overwritten every frame.
   - Fix: record only when the caller is FrameRunDemo.
2. **Cutscene code runs from the KUSEG mirror.** ra = `0x0007D8B4`, not `0x8007D8B4`, and data pointers can be `0x00xxxxxx`.
   - Fix: compare return addresses with the segment bits masked, and normalise every pointer to KSEG0 before validating or writing it.
   - This took three test rounds to find. The log line that cracked it printed the raw `ra` value.
3. **Scripted in-engine scenes are not DMO cutscenes.** The escape sequence runs with the player actor alive, so walk-mode Snake's eyes simply continues. The owner first thought the cutscene feature worked from that.
   - Lesson: log *which* path drove the camera.

**For GOG:**
- The PC build has no mirror, but the "two camera updates per frame" trap probably applies. GOG's notes already say "the layer-3 hook is skipped while bit 0x80 is set".
- Check the facing method: column 2 of joint 6 is a cheap, exact facing source and doesn't need DMO_ADJ rots.

### 3.7 Body follows head

- **MC data:**
  - GM_PlayerControl → CONTROL; rot.vy at +0xA, turn.vy at +0x4E (CONTROL is at actor+0x20, so +0x2A and +0x6E as in GOG).
  - GM_SnakeCamera.rotate2 is a copy of control.rot.
- **Design:** only when the move stick is idle and GM_PlayerStatus has none of these set:
  - MOVE, GROUND, NOT_PLAYABLE, DAMAGED, DOWNED, ATTACK, CB_BOX, GAME_OVER;
  - CAUTION (wall), CHECK_WALL, WATER, PAD_OFF, WATCH, NORMAL_WATCH.

  When the look heading differs from rot.vy by more than 30°, rotate both rot.vy and turn.vy toward it at 360°/s. Owner-confirmed.
- **For GOG:** the status-flag gate is a clean way to avoid fighting wall-press, crawl and box states.

### 3.8 Settings panel (GDI text in a quad)

- Hold the left menu button 0.7 s. A short press still sends Start, on release, held 120 ms so a 30 fps frame sees it.
- Draw text with GDI (Segoe UI) into a DIB section, then UpdateSubresource into a BGRA texture, then blit into the quad swapchain.
- Every change writes the ini and forces an immediate reload.
- **Bug worth knowing:** under mingw, `swprintf(L"%s", wchar_t*)` printed only the first character. It must be `%ls`.

### 3.9 INI handling trap

- `GetPrivateProfileString` reads only the **first** section with a given name. Appending a second `[walk]` block silently does nothing.
- Add new keys with `WritePrivateProfileString` into the existing section.

### 3.10 Menus outside the game (DirectInput wrapper)

- Patch IDirectInput8::CreateDevice (vtable 3). For the system keyboard device, patch GetDeviceState (9) and GetDeviceData (10).
- **Store the original per vtable**: the ANSI and wide interfaces have separate vtables.
- Inject keys only while the game itself isn't consuming the pad. Log real key presses only in menus, only with the game focused, and capped (privacy).
- GOG's equivalent ("Codec and Pause go out as Tab and Esc") could use the same wrapper, instead of SendInput, if focus is ever an issue.

### 3.11 Wrist panels (Integral layout, now ported)

- **Layout:**
  - Left wrist: LIFE, radar, item box.
  - Right wrist: weapon box with ammo.
  - Each panel shows within a 28° gaze cone.
- The grip pose comes from OpenXR action spaces. The ini names match the Integral mod: `[wrist_hud]` width_mm, left/right_offset_cm, left/right_rotation_deg, gaze_cone_deg, and the crop fractions.
- One swapchain carries both panels (left half and right half sub-rects): one acquire per frame for two quads.
- Floating screen per pause type:
  - GV_PauseLevel bit 1 = codec, movies, game over;
  - bit 2 = pause;
  - bit 4 = item and weapon menus.

  Each is switchable. When a switch is off, the frozen view keeps its last tagged pose. The screen is placed where you look when it opens.

### 3.12 Process lessons (apply to any port)

- **Generate and verify, never hand-assemble.** Emulate every routine against real RAM snapshots from both versions, including edge cases (KUSEG callers, double calls per frame, a relink in the same frame).
- **Make every build diagnose itself.** Each test round should return a log that says *why*. Examples: the raw `ra`, "matched / missed" counts, hold-trigger counts, PERF verdicts.
  - Three of our biggest wins came from one log line each: PERF, MARKER/POSE, and the raw caller address.
- **Ship to a new versioned folder every build** and check the size on the PC. When two builds have the same size (it happened: panel v1 and v2), compare checksums.
- **Ask the logs, not the eyes.** "Some cutscenes were in first person" was the walk mode, not the cutscene code. The log showed no cutscene path had run.

## 4. Recommended improvements for the GOG mod, in priority order

1. **Exact per-picture tags via an in-frame marker:**
   - eye plus head-pose number (3.2, 3.4);
   - validator plus data tiles, strip-limited decode, read from a staging copy taken with the frame.
   - Expected wins:
     - no eye mix-ups;
     - no pose lag doubling or shimmer;
     - simpler hold and timeout logic;
     - retire "capture skip count must be odd".
2. **Audit the capture-to-submit hand-off for hidden GPU waits** (3.1). Replace any keyed mutex or cross-device wait with completed-copy publishing (EVENT queries) and a 3-slot ring.
   - Then re-test the "quad layers collapse the frame rate" belief.
3. **Add PDH performance logging** (GPU 3D total and this-process share, video encode, CPU, network send) with a verdict line.
4. **Re-check the motion-hold sampling:** per game frame, same-eye comparison, trigger counts logged.
5. **Flush after End(query)** wherever queries are polled with DONOTFLUSH.
6. **Cutscene camera:** head facing from joint-6 column 2. Log the camera path per frame, so scripted scenes and demo cutscenes are never confused.
7. **Settings and INI hygiene:** `%ls` for wide strings, and no duplicate ini sections.

### 5.2 Structures

- **DG_CHANL (0x1EC):**
  - ot[2] +0, ot_size +8, link +A, dblbuf +C;
  - eye_inv +0x10, eye +0x30, screen +0x50;
  - env1, env2, new_env (DR_ENV 0x40 each).
  - Overlay chanl[2]: ot_size 0, link 8. Prims added to `ot[GV_Clock][0]` draw on top of the scene.
- **DG_OBJS:**
  - world +0, root +0x20, def +0x24, flag +0x28 (0x80 invisible), n_models +0x2E;
  - objs[] +0x48 (DG_OBJ stride 0x5C, world at +0).
  - Joint 6 (head): world matrix +0x270, t +0x284.
- **CONTROL (0x7C):**
  - mov +0, rot +8 (rot.vy +0xA), evt +0x10, map +0x2C;
  - step +0x44, turn +0x4C (turn.vy +0x4E).
- **GV_PAD (0x10 per pad):**
  - status +0, press +2, release +4, quick +6, dir +8, analog +0xA;
  - right_dx/dy +0xC/+0xD, left_dx/dy +0xE/+0xF.
  - [0] = pad 1 configured, [2] = pad 1 raw.
- **MGSDEMOACT:** header +0x30, models +0x34, control +0xC4.
- **DMO_DEF:** n_models +0x10, models +0x18.
- **DMO_MDL** (0x14): filename +0xC.
- **DEMO_MODEL** (0x1A4): objs +0x7C.
- **TILE packet** (marker): tag (len 3), `0x60BBGGRR`, `y<<16|x`, `h<<16|w`.
- **GV_PauseLevel bits:**
  - 1 STOP (codec, movies, game over);
  - 2 PAUSE;
  - 4 MENU (item and weapon);
  - 8 READERROR.

### 5.3 Frame order (decomp)

1. GV daemon: `GV_Time++`, `GV_Clock ^= 1`.
2. DG_StartFrame: draws OT[1−W], clears OT[W].
3. GV_UpdatePadSystem (our pad hook).
4. Actors, including the camera, FrameRunDemo and our camera routine.
5. DG_EndFrame: DG_SortChanlSystem(W).
